# CRAVE backend — NOT Railway's build entry point, despite this file's
# previous header claiming otherwise. That claim was wrong and caused a
# real production outage: Railway's Railpack builder auto-detects Python
# and, as an optimization, copies ONLY this top-level requirements.txt
# into the build context before running `pip install -r requirements.txt`
# — it does not resolve `-r` references to other files first. Collapsing
# this file to `-r backend/requirements.txt` (the previous fix for a real
# drift problem — see git history) made pip try to open
# /app/backend/requirements.txt, which hadn't been copied into the build
# context yet at that point, and every deploy failed with "No such file
# or directory" until this was caught from an actual Railway build log,
# not local testing (a local `pip install --dry-run` from repo root has
# the whole filesystem present and can't reproduce Railway's staged copy
# order).
#
# The actual install command Railway runs is now pinned explicitly in
# railpack.json at the repo root, which references backend/requirements.txt
# directly with no indirection through this file to get confused about.
#
# This file still exists for local convenience — `pip install -r
# requirements.txt` from repo root on a normal (non-staged) filesystem
# works fine and picks up backend/requirements.txt correctly, since the
# whole repo is already present on disk. Just don't assume this is what
# Railway itself installs from — check railpack.json for that.
-r backend/requirements.txt
